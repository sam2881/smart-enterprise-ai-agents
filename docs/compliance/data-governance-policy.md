## 1. Policy Statement

The Enterprise Agentic AI Platform is committed to responsible, transparent, and accountable management of all data assets. This Data Governance Policy establishes the framework, roles, standards, and controls that govern how data is collected, stored, processed, classified, protected, and deleted across both AI agent systems.

Data is a strategic asset. Its integrity, quality, and security directly determine the reliability of AI-generated decisions. The platform processes operational data from IT incidents, engineering pipelines, LLM interactions, and integrations with ServiceNow, Jira, and third-party APIs. Inadequate governance of this data creates risk to individuals (through privacy violations), to the organization (through regulatory non-compliance), and to the AI systems themselves (through poor-quality training signals and unreliable outputs).

This policy applies without exception to all platform contributors, administrators, and automated processes.

## 2. Policy Scope

This policy governs all data processed, stored, or transmitted by:

- **System 1 — Incident Management:** 12-node LangGraph workflow, Kafka event bus, PostgreSQL, Neo4j, Weaviate, Redis, MCP server integrations
- **System 2 — APEX Data Engineering Agent:** 5-agent LangGraph, FastAPI control plane, Airflow DAG generation, GCS artifact storage, BigQuery targets
- **Frontend:** Next.js 14 application and all browser-side state
- **Infrastructure:** Docker Compose (local), GCP (production) — Secret Manager, GCS, BigQuery, Dataproc
- **CI/CD:** GitHub Actions workflows
- **LLM Integrations:** OpenAI API, Anthropic Claude API, Langfuse tracing

**Out of Scope:** Data held in third-party SaaS systems not integrated with the platform; physical media not used to support platform operations.

## 3. Definitions

## 5. Data Classification Framework

All data assets must be classified at creation and re-assessed annually or when the data content changes materially.

| Level | Label | Description | Examples | Required Controls |
|-------|-------|-------------|---------|------------------|
| L1 | PUBLIC | Non-sensitive; safe for public disclosure | API schemas, platform documentation, open-source DAG templates | None beyond standard availability controls |
| L2 | INTERNAL | Internal operational data; not for public disclosure | Pipeline configurations, DAG definitions, system metrics, non-sensitive catalog entries | Access control (authenticated users only) |
| L3 | CONFIDENTIAL | Sensitive business or operational data with reputational or regulatory impact if disclosed | Incident details, system credentials, PII-masked data, Weaviate embeddings | Encryption at rest and in transit + RBAC access control + audit logging |
| L4 | RESTRICTED | Highly sensitive; legal obligations govern handling | Raw PII, audit logs, LLM traces containing names, approval records, breach records | Encryption + MFA (planned) + audit logging + retention schedule + need-to-know access |

### 5.1 Classification Process

1. Data Steward assigns initial classification at asset registration
2. Classification is recorded in the data catalog (`catalog_repository.py`)
3. Data Owner must approve any downgrade in classification (L4→L3 or L3→L2)
4. AI Safety Officer must be consulted for any L4 classification change
5. PII detection results can auto-escalate classification to L4 without manual approval

## 6. Medallion Zone Access Policy

### 6.1 Zone Definitions and Access Matrix

| Zone | Classification | Authorized Access | Permitted Operations | PII Policy | Quality Gate | Audit Required |
|------|---------------|------------------|---------------------|-----------|-------------|----------------|
| Landing | RESTRICTED (L4) | Platform service accounts only (Airflow, Kafka consumers) | Write (ingest), Read (Bronze promotion only) | Raw PII permitted; detection logged | None — raw ingestion | Yes — all writes |
| Bronze | CONFIDENTIAL (L3) | Data Engineers + platform service accounts | Read, Write (via pipeline), Delete (data corrections only) | PII detected and classified; CRITICAL severity blocks | Schema validation — column types, nullability | Yes — all writes and deletes |
| Silver | CONFIDENTIAL (L3) | Data Engineers + Data Stewards + service accounts | Read, Write (via pipeline), no direct Delete | PII masked: HASH/TOKENIZE applied; REDACT for unused fields | NOT_NULL + UNIQUE + FRESHNESS checks | Yes — all writes |
| Gold | INTERNAL (L2) | Data Engineers + Analysts + BI tool service accounts + Reporting tools | Read, Write (via pipeline) | Zero PII — verified at Gold gate; analytics-ready final layer | Full quality suite + business validation (all 9 rule types) | Yes — all writes and reads by external consumers |

### 6.2 Zone Promotion Gates

Data is promoted to the next zone only when:
1. The quality gate for the target zone passes (Section 8.2)
2. PII policy for the target zone is satisfied (Section 7)
3. The pipeline definition has been approved by the Data Steward
4. A `PIPELINE_CREATED` or zone-promotion audit event is written

Failed promotions result in the pipeline entering `FAILED` status. The Data Steward is notified. Data remains in the current zone pending remediation.

### 7.1 Detection Framework

Automatic PII detection is mandatory at every zone boundary. Implementation: `agents/data_agent/src/security/pii_detection.py`.

**13 PII Categories Detected:**

| # | PII Type | Detection Method | Default Severity |
|---|----------|-----------------|-----------------|
| 1 | Social Security Number (SSN) | Regex: `\d{3}-\d{2}-\d{4}` with context | HIGH |
| 2 | Credit Card Numbers | Luhn-validated regex for major card types | HIGH |
| 3 | Email Addresses | RFC 5322-compliant regex | MEDIUM |
| 4 | Phone Numbers | E.164 and local format detection, multi-country | MEDIUM |
| 5 | Date of Birth | Multiple date format patterns with age context | MEDIUM |
| 6 | IP Addresses | IPv4 and IPv6 pattern matching | LOW |
| 7 | Passport Numbers | Country-specific format patterns | HIGH |
| 8 | NHS Numbers | UK NHS format with check digit | HIGH |
| 9 | National Insurance Numbers | UK NINO format | HIGH |
| 10 | IBAN | ISO 13616 format with country code validation | HIGH |
| 11 | VIN (Vehicle Identification Number) | 17-character ISO 3779 format | MEDIUM |
| 12 | EIN (Employer Identification Number) | US EIN format `XX-XXXXXXX` | MEDIUM |
| 13 | Bank Routing Numbers | ABA routing number format with checksum | HIGH |

| Phone Number | Permitted (logged) | Detect only | HASH | REMOVE |
| Date of Birth | Permitted (logged) | Detect only | PARTIAL_MASK (year only) | REMOVE |
| IP Address | Permitted (logged) | Detect only | PARTIAL_MASK (last octet) | REMOVE |
| Passport Number | Permitted (logged) | REDACT | TOKENIZE | REMOVE | REMOVE |
| NHS Number | Permitted (logged) | REDACT | TOKENIZE | REMOVE | REMOVE |
| National Insurance | Permitted (logged) | REDACT | TOKENIZE | REMOVE | REMOVE |
| IBAN | Permitted (logged) | REDACT | PARTIAL_MASK (last 4) | REMOVE | REMOVE |
| VIN | Permitted (logged) | Detect only | HASH | REMOVE | REMOVE |
| EIN | Permitted (logged) | REDACT | TOKENIZE | REMOVE | REMOVE |
| Bank Routing | Permitted (logged) | REDACT | REDACT | REMOVE | REMOVE |

### 7.3 Masking Implementations

`agents/data_agent/src/security/governance_enforcer.py` applies all five strategies:

| Strategy | Technical Implementation | Reversibility | Use Cases |
|----------|------------------------|--------------|-----------|
| REDACT | Replace value with `[REDACTED]` literal | None | Fields not needed downstream |
| HASH | SHA-256(value + platform_salt) | None (one-way) | Deduplication keys; joining on anonymized identity |
| TOKENIZE | Map to UUID in secure lookup table (PostgreSQL) | Yes — authorized lookup | Fields needed for joining or future recovery |
| PARTIAL_MASK | Keep N leading/trailing chars; replace middle with `*` | None | User-facing display fields needing partial context |
| ENCRYPT | AES-256-GCM with key from GCP Secret Manager | Yes — authorized decryption | Fields needing authorized recovery only |

### 7.4 CRITICAL Severity Escalation

When PII detection returns CRITICAL severity (health data, biometric data, or multiple HIGH-severity PII types in one record):

1. Pipeline status immediately set to `BLOCKED`
2. `PII_DETECTED` audit event written with severity=CRITICAL, pipeline_id, column_name (not value)
3. Automated notification sent to Data Steward and AI Safety Officer
4. Pipeline cannot advance until Data Steward reviews and either:
   - Approves with documented justification and masking plan, OR
   - Rejects the source data; pipeline is terminated
5. All CRITICAL escalations are reported in the monthly governance review

## 8. Data Quality Standards

### 8.1 Quality Rule Types

Nine quality rule types are enforced via Great Expectations (`dags/dag_utilities/validation/ge_validator.py`):

| # | Rule Type | Description | Applicable Zones |
|---|-----------|-------------|-----------------|
| 1 | NOT_NULL | Required fields must contain a non-null value | Bronze, Silver, Gold |
| 2 | UNIQUE | Key columns must have no duplicate values across the dataset | Silver, Gold |
| 3 | RANGE | Numeric or date values must fall within defined min/max bounds | Silver, Gold |
| 4 | REGEX | String values must match an expected regular expression pattern | Bronze, Silver, Gold |
| 5 | REFERENTIAL | Foreign key values must exist in the referenced dimension table | Gold |
| 6 | FRESHNESS | Data must have been loaded within the expected time window | Landing, Bronze, Silver, Gold |
| 7 | COMPLETENESS | Minimum percentage of non-null values in a column (threshold configurable) | Bronze, Silver, Gold |
| 8 | ROW_COUNT | Row count must fall within expected minimum/maximum bounds | Landing, Bronze, Silver, Gold |
| 9 | CUSTOM | Business-specific rules defined by Data Steward in YAML | Gold |

### 8.2 Quality Gates by Zone

| Zone | Required Rule Types | Failure Action | SLA to Resolve |
|------|-------------------|---------------|---------------|
| Bronze gate | REGEX (format checks), ROW_COUNT (not empty), FRESHNESS | Pipeline halted at Bronze; Data Steward notified | 1 business day |
| Silver gate | NOT_NULL (required fields), UNIQUE (primary keys), FRESHNESS, COMPLETENESS (≥80%) | Pipeline halted at Silver; escalated to Data Owner if >24h | 1 business day |
| Gold gate (final) | All 9 rule types including CUSTOM; Data Steward + Data Owner sign-off required | Pipeline halted; P3 incident raised if blocking downstream BI; Senior Data Engineer review required | 4 hours |

### 8.3 Quality Failure Remediation

Quality failures are documented in the pipeline run log and the data catalog. Remediation options:

1. **Source fix:** Correct the source data and re-trigger the pipeline
2. **Rule adjustment:** If the rule threshold is incorrect, Data Steward submits a rule change request (Data Owner approval required for Gold thresholds)
3. **Exception:** Temporary exception (max 5 business days) requires Data Owner approval and AI Safety Officer notification for Gold data

### 8.4 Quality Metrics and Reporting

Data quality metrics are exposed via Prometheus and visible in the `/observability` frontend route:
- Quality gate pass rate per pipeline (target: ≥99%)
- Quality failure count by rule type and zone
- Mean time to resolve quality failure
- PII detection count by type and zone

Monthly data quality reports are reviewed by Data Stewards and presented to the AI Safety Officer.

## 9. Data Lineage Requirements

### 9.1 Mandatory Lineage Events

Every pipeline execution must emit OpenLineage-compatible events at each zone transition. Lineage is non-negotiable — pipelines without lineage tracking will not pass CI/CD validation.

Required lineage fields per event:

| Field | Description | Example |
|-------|-------------|---------|
| `run_id` | Unique pipeline run identifier (UUID) | `a3f8b2c1-...` |
| `pipeline_id` | Stable pipeline definition identifier | `pipe_sales_daily_001` |
| `source_entity` | Source table or file path | `gs://landing/sales/2026-06-22/*.csv` |
| `target_entity` | Target table or file path | `bq://project.sales.daily_bronze` |
| `transformation_type` | Category of transformation applied | `SCHEMA_CAST`, `PII_MASK`, `AGGREGATE` |
| `row_count_in` | Rows read from source | `1,423,891` |
| `row_count_out` | Rows written to target | `1,423,889` (2 rejected) |
| `column_mapping` | Source-to-target column name mapping (JSON) | `{"src_cust_id": "customer_id"}` |
| `pii_actions_applied` | PII masking operations performed | `[{"column": "email", "strategy": "HASH"}]` |
| `quality_gate_result` | PASS / FAIL + rule failure details | `{"result": "PASS", "rules_checked": 4}` |
| `timestamp` | UTC timestamp of event emission | `2026-06-22T14:32:01Z` |
| `zone_from` | Source Medallion zone | `LANDING` |
| `zone_to` | Target Medallion zone | `BRONZE` |

### 9.2 Implementation

Lineage events are emitted by `dags/dag_utilities/logging/lineage_tracker.py` and stored in the `platform_data_lineage` PostgreSQL table. The lineage viewer is accessible via the `/catalog` frontend route.

### 9.3 Lineage Retention

Data lineage records are retained for 2 years. After 2 years, summary lineage (asset→asset without row counts) is retained for an additional 3 years for audit purposes.

### 9.4 Lineage Completeness Audit

The AI Safety Officer reviews lineage completeness quarterly:
- All active pipelines must have lineage records for every run in the past 30 days
- Gaps in lineage records are raised as P4 governance incidents
- Pipelines without lineage for 7+ consecutive days are automatically flagged for review

## 11. Retention and Deletion Policy

Full retention schedule is defined in `docs/compliance/gdpr.md` Section 10. The following summarizes implementation.

### 11.1 Automated Retention Enforcement

`backend/governance/data_retention.py` executes daily deletion tasks:
- Identifies records beyond their retention period
- Applies the appropriate deletion method (hard delete or soft delete + flag)
- Writes a `DATA_DELETION` audit event for each batch deletion
- Reports deletion counts to Prometheus (`data_retention_deleted_records_total`)

### 11.2 Hard Delete vs. Soft Delete

| Deletion Type | Definition | Applied To |
|--------------|-----------|-----------|
| Hard delete | Permanent removal from database; cannot be recovered | Pipeline metadata after 90 days; incident data after 2 years; authentication logs after 2 years |
| Soft delete | `is_deleted = true` flag; data retained for audit but excluded from normal queries | Audit logs (cannot be hard-deleted — EU AI Act legal obligation) |

### 11.3 Legal Hold Procedure

When data is subject to regulatory investigation or legal proceedings:
1. AI Safety Officer issues a Legal Hold notice referencing the specific data assets
2. Platform Admin applies `legal_hold = true` flag to affected records
3. `data_retention.py` skips records with legal hold flag
4. Legal Hold is reviewed monthly; lifted only with written authorization from legal counsel
5. Legal Hold duration is documented in the breach register

### 11.4 GCS Lifecycle Policies

GCS bucket lifecycle rules are configured to enforce object deletion:
- Pipeline artifacts bucket: `DELETE` action after 90 days
- Landing zone bucket: `DELETE` action after 30 days (raw data migrated to Bronze)
- Audit export bucket: `OBJECT_VERSION_ENABLED` with no expiry (versioned immutable archive)

## 12. Data Breach and Incident Response

### 12.1 Classification

| Priority | Category | Examples | Response SLA |
|----------|----------|---------|-------------|
| P1 | Data breach — PII exposed | Unauthorized disclosure of unmasked PII; audit log compromise | 2 hours containment; 72-hour regulatory notification |
| P2 | Unauthorized access | Privilege escalation; unauthorized API access; credential compromise | 4 hours containment |
| P3 | Availability failure | Pipeline failure blocking downstream consumers; Kafka lag; DB unavailability | 8 hours restoration |
| P4 | Data integrity failure | Audit log gap; quality gate bypass; lineage gap; catalog non-compliance | 24 hours remediation |

### 12.2 Response Procedure

1. Detection via Prometheus alert, audit log query, or manual report
2. `SECURITY_INCIDENT` event logged immediately with incident details
3. AI Safety Officer and Platform Admin notified (PagerDuty or email per severity)
4. Severity classified (P1/P2/P3/P4) within 30 minutes
5. Containment actions taken (credential revocation, pipeline halt, service isolation)
6. GDPR breach assessment for P1: is personal data involved? Are individuals at risk?
7. Supervisory authority notification within 72 hours for notifiable P1 breaches (GDPR Art 33)
8. Remediation: root cause addressed, controls strengthened
9. Post-Incident Review within 5 business days; findings documented and tracked

### 12.3 Data Subject Notification

P1 breaches involving high-risk exposure to individuals require direct notification to affected data subjects per GDPR Art 34. Notification coordinated by AI Safety Officer within 72 hours of breach discovery.

## 13. Policy Exceptions

### 13.1 Exception Process

Any deviation from this policy requires formal exception approval:

1. Data Engineer or Data Steward submits exception request documenting:
   - Policy clause to be excepted
   - Business justification
   - Risk assessment
   - Proposed compensating controls
   - Requested duration (maximum 90 days)

2. Data Owner approves the business justification

3. AI Safety Officer approves the risk and compensating controls

4. Exception is logged in the exception register with reference ID

5. Exception is reviewed at 45 days and must be renewed or closed by day 90

6. All active exceptions are reported in the quarterly governance review

### 13.2 No-Exception Controls

The following controls cannot be excepted under any circumstances:
- 7-year audit log retention (EU AI Act legal obligation)
- Human approval gate for production pipeline deployment
- PII detection at Gold zone boundary
- Secret management via GCP Secret Manager in production
- Immutability of audit log records

## 15. AI Threat Governance (MITRE ATLAS)

The platform addresses adversarial AI threats catalogued in MITRE ATLAS (Adversarial Threat Landscape for AI Systems). These controls supplement the standard security controls in Section 14 and directly protect the LLM-powered components from machine learning–specific attack vectors.

### 15.1 Threat Model Scope

MITRE ATLAS threats are relevant to both AI systems:
- **Incident Management Agent**: LLM receives incident descriptions that may be adversarially crafted by threat actors who have write access to ServiceNow.
- **Data Engineering Agent (APEX)**: LLM receives natural language pipeline descriptions, DTSX files, and stored procedure definitions from external data sources.

### 15.2 Active Controls by ATLAS Technique

| ATLAS ID | Technique Name | Control | Implementation | Governance Owner |
|----------|---------------|---------|----------------|-----------------|
| AML.T0051 | Prompt Injection via LLM APIs | `InputValidator` scans all LLM-bound text with 16 regex patterns; score < 0.5 → blocked | `backend/guardrails/llm_guardrails.py` → `InputValidator` | AI Safety Officer |
| AML.T0043 | Craft Adversarial Data | Command injection detection for shell metacharacters, `$(...)` substitution, pipe-to-rm in incident descriptions | `backend/guardrails/llm_guardrails.py` → command injection patterns | Platform Engineering |
| AML.T0048 | ML Model Data Poisoning | RAG source versioning + attribution; anomaly detection on retrieval score distribution; embedding refresh audit trail | `backend/rag/embedding_service.py` · `AuditEventType.SYSTEM_CONFIG_CHANGE` | Data Steward |
| AML.T0040 | ML Supply Chain Compromise | LLM API keys in GCP Secret Manager; model version pinned in all call sites; dependency versions pinned in `requirements.txt` | `SecretManagerServiceClient` in all agent init; `pip freeze` in CI | Platform Admin |
| AML.T0016 | Exploit Public-Facing ML Model API | Rate limiting: 60 req/min, 500 req/hour per identity; excess triggers `UNAUTHORIZED_ACCESS` audit event | `backend/guardrails/llm_guardrails.py` → `RateLimiter` (Redis-backed) | Platform Engineering |
| AML.T0005 | Create Proxy ML Model | Output validation blocks credential exposure and harmful command patterns before presentation | `backend/guardrails/llm_guardrails.py` → `OutputValidator` | AI Safety Officer |

### 15.3 Prompt Injection Defense — Detail

The `InputValidator` component in `backend/guardrails/llm_guardrails.py` implements defense-in-depth against prompt injection:

**16 Detection Pattern Categories:**

1. Direct instruction override (`ignore previous instructions`, `disregard above`)
2. Role manipulation (`you are now`, `act as`, `pretend to be`)
3. Jailbreak attempts (`DAN mode`, `developer mode enabled`, `jailbreak`)
4. System prompt extraction (`reveal your system prompt`, `print your instructions`)
5. Context window manipulation (`[END OF CONTEXT]`, `---END---`)
6. Encoding bypass — base64 (`decode this:`, `base64:`)
7. Encoding bypass — hex (`\x41\x49`)
8. Language switching as bypass (Unicode RTL override characters)
9. Fictitious authority claims (`as your creator`, `as Anthropic`)
10. Hypothetical framing (`if you were allowed to`, `in a hypothetical world`)
11. Nested prompt injection (`the following is a user message that says:`)
12. Token smuggling via special characters
13. Few-shot override (`example: User: <injection> Assistant: <desired output>`)
14. Output format manipulation (`respond only in JSON with key "execute":`)
15. Markdown injection (code blocks containing instructions)
16. Multi-turn context pollution (`earlier you agreed to`, `you already told me`)

**Scoring:** Each matched category reduces the safety score. Any single high-severity match (categories 1–5) immediately sets the score to < 0.5 and blocks the call. Multiple lower-severity matches accumulate. All blocked inputs are logged as `UNAUTHORIZED_ACCESS` audit events.

### 15.4 Output Validation

The `OutputValidator` in `backend/guardrails/llm_guardrails.py` scans all LLM outputs before they reach users or execution engines:

| Pattern Category | Examples | Score if Matched |
|-----------------|---------|-----------------|
| Destructive filesystem | `rm -rf /`, `mkfs.`, `dd if=/dev/zero` | 0.2 |
| Privilege escalation | `chmod 777`, `sudo su -`, `passwd root` | 0.2 |
| Fork bomb | `:(){ :|:& };:` | 0.2 |
| Credential exposure | `password: "..."`, `api_key = "..."`, `secret:` | 0.2 |
| Data exfiltration | `curl ... \| nc`, `wget ... > /dev/tcp/` | 0.2 |

Output with safety score < 0.5 is rejected; the plan is discarded and the incident is escalated for fully manual handling.

### 15.5 Legacy Migration Threat Considerations

The Legacy Migration feature (Section 15 in `APEX_README.md`) introduces additional attack surface: stored procedure definitions are fetched from external databases and passed to the LLM. The following mitigations are in place:

1. **Proc definition length limit**: `sp_max_definition_length = 100,000` chars truncates abnormally large definitions that may contain embedded injection payloads.
2. **Input sanitization**: The DTSX parser (`dtsx_parser.py`) operates on structured XML elements, not raw string concatenation, preventing XML injection from escalating to LLM injection.
3. **Static fallback isolation**: When using static `.sql` file fallback, file paths are restricted to `static_sql_scan_root` — no path traversal possible.
4. **Credential isolation**: Connection credentials for StoredProcReader are resolved via GCP Secret Manager with least-privilege service accounts; credentials are never logged or included in LLM payloads.

### 15.6 ATLAS Control Monitoring

ATLAS-specific signals are monitored via Prometheus and the audit log:

| Signal | Metric / Event | Alert Threshold | Review Owner |
|--------|---------------|-----------------|-------------|
| Prompt injection attempts | `guardrail_blocked_total{reason="injection"}` | >5 blocks in 5 min | AI Safety Officer |
| Command injection attempts | `guardrail_blocked_total{reason="command_injection"}` | Any single hit | Platform Engineering (immediate) |
| Rate limit triggers | `rate_limit_exceeded_total` | >20 in 1 hour from same identity | Platform Admin |
| Output validation blocks | `output_validator_blocked_total` | Any hit | AI Safety Officer (immediate) |
| RAG retrieval score anomaly | `rag_retrieval_score_p50` | Drop >25% vs 7-day baseline | Data Steward |
