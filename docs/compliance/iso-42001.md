## 1. Scope and Purpose

### 1.1 Purpose of this Document

This document assesses the Enterprise Agentic AI Platform's conformity with ISO/IEC 42001:2023 (AI Management System — AIMS). It serves as:

- The foundational AIMS documentation required by Clause 7.5 (Documented Information)
- The primary evidence base for future ISO 42001 certification engagement
- The internal governance reference for AI system management practices
- A gap analysis for the actions required prior to seeking formal third-party certification

### 1.2 AI Systems in Scope

Both AI systems on the Enterprise Agentic AI Platform are within the scope of this AIMS:

| AI System | Description | Classification |
|-----------|-------------|----------------|
| Incident Management Agent | 12-node LangGraph StateGraph automating IT incident detection, triage, classification, plan generation, human approval, execution, and closure. Integrated with ServiceNow. | HIGH-RISK (EU AI Act Annex III) |
| Data Engineering Agent (APEX) | 5-agent LangGraph pipeline automating data pipeline design, code generation, validation, and deployment across 70+ source types in the medallion architecture. | HIGH-RISK (EU AI Act Annex III) |

### 1.3 Scope Boundary

**In scope:**
- Both AI agent systems described above
- All LLM API integrations (OpenAI GPT-4, Anthropic Claude)
- All supporting governance, guardrails, audit, and data governance modules
- Frontend approval and oversight interfaces
- Data infrastructure used by the Data Engineering Agent (APEX)

**Out of scope:**
- AI/ML models used by third-party providers (OpenAI, Anthropic, GCP) — governed by supplier management (Clause 8.7)
- Non-AI software components (authentication services, logging infrastructure not related to AI outputs)
- AI systems operated by customers or third parties

### 1.4 AIMS Objectives

The primary objectives of the AI Management System are:

1. Ensure responsible and trustworthy AI development and operation
2. Demonstrate compliance with the EU AI Act (Regulation (EU) 2024/1689)
3. Provide adequate human oversight of all consequential AI decisions
4. Protect data subjects through PII detection, masking, and retention controls
5. Continuously improve AI system performance, safety, and explainability

## 2. Clause 4: Context of the Organization

### 4.1 Understanding the Organization and Its Context

**Organizational Context:**

The Enterprise Agentic AI Platform is an enterprise software platform operated by an internal Platform Engineering team. The platform serves two primary operational domains:

1. **IT Operations:** The Incident Management Agent automates the response to IT infrastructure incidents, reducing mean-time-to-resolution (MTTR) for production systems while ensuring human sign-off before any remediation action affects production.

2. **Data Engineering:** The Data Engineering Agent (APEX) reduces data pipeline development cycle time from days to minutes by generating validated, deployment-ready Apache Spark and Cloud Dataflow pipelines for 70+ source data types across the full medallion architecture.

**External Context:**
- Regulatory environment: EU AI Act (Regulation (EU) 2024/1689) — applicable from 2 August 2026
- GDPR compliance requirements for PII data processed through pipelines
- Dependence on third-party AI model providers (OpenAI, Anthropic, GCP Vertex AI)
- Rapidly evolving AI capability and risk landscape

**Internal Context:**
- Event-driven architecture with Kafka as the system of record — all state transitions flow through Kafka topics, providing a reliable audit trail
- Human-in-the-loop approval gates are structurally enforced via Kafka event-driven pause/resume, not convention
- Infrastructure runs on GCP (Cloud Composer, BigQuery, Cloud Storage, Pub/Sub)
- PostgreSQL for metadata, audit logs, and data catalog

### 4.3 Determining the Scope of the AIMS

The AIMS covers both AI systems described in Section 1.2, all supporting governance infrastructure, and all processes involved in the AI system lifecycle from development through post-market monitoring.

The scope was determined by:
1. Identifying all systems that use AI/ML to make or support consequential decisions
2. Assessing the risk level of each system's outputs
3. Including all systems classified as HIGH-RISK under the EU AI Act

This scope is reviewed annually and upon any introduction of new AI capabilities.

### 4.4 AI Management System

The AIMS is structured around the following governance pillars:

1. **Risk Management:** `backend/governance/eu_ai_act_compliance.py` — Article-by-article compliance tracking and decision validation
2. **Guardrails:** `backend/guardrails/llm_guardrails.py` — Input/output validation for all LLM calls
3. **Audit and Record Keeping:** `backend/governance/audit_logger.py` — 18 event types, 7-year retention
4. **Data Governance:** `backend/governance/data_retention.py`, `agents/data_agent/src/security/pii_detection.py`
5. **Human Oversight:** `backend/orchestrator/langgraph_workflow.py` → `node_await_approval`
6. **Post-Market Monitoring:** Prometheus + Grafana + Langfuse

## 6. Clause 8: Operation

### 8.1 Operational Planning and Control

Both AI systems follow a structured development and deployment process:

**Incident Management Agent — Operational Flow:**
```
ServiceNow Incident → Kafka (incident.created)
  → EventOrchestrator → LangGraph workflow
    → ingest → parse → classify → swarm_rag → generate_plan
    → judge → control_plane → await_approval [HUMAN GATE]
    → execute → verify → close_ticket → feedback_loop
  → Kafka (incident.closed)
```

**Data Engineering Agent (APEX) — Operational Flow:**
```
User/Jira Trigger → UnifiedPipelineInput API (POST /api/v2/data-agent/pipelines)
  → LangGraph workflow
    → supervisor → planner → generator → validator [HUMAN GATE]
    → deployer (PROD requires approval)
  → Cloud Composer DAG deployed
```

Operational controls include:
- Kafka as system of record — no state exists outside Kafka events
- All LLM calls wrapped in guardrails (Section 3.3 of the EU AI Act document)
- Human approval required before PROD deployment in both systems
- Prometheus metrics collected throughout for operational monitoring

### 8.2 AI System Impact Assessment

The EU AI Act compliance module (`backend/governance/eu_ai_act_compliance.py`) serves as the platform's AI System Impact Assessment (AISA) tool:

- `EUAIActCompliance.validate_decision()` performs pre-execution impact validation for every AI decision
- Decision validation checks human oversight presence for high/critical risk decisions
- Confidence threshold checks prevent low-confidence actions from executing
- The `AIActRiskCategory` enum captures the system's risk classification

A formal standalone AI System Impact Assessment document is referenced in `docs/compliance/eu-ai-act.md` (this document + the EU AI Act assessment together constitute the AISA).

**GAP:** The impact assessment is currently embedded in code and compliance documentation rather than being a standalone governed document with stakeholder sign-off. This is Gap G-004 in Section 10.

### 8.3 AI System Lifecycle Management

**Development Phase:**
- Feature branches with code review (pull request required before merge)

**PR Validation:**

**Staging Deployment:**

- APEX pipelines validated against staging BigQuery datasets
- Performance metrics validated against targets in Section 6.2

**Human Approval (PROD):**
- All PROD deployments require explicit human approval
- Incident Management Agent: `node_await_approval` Kafka pause/resume
- Data Engineering Agent: PROD deploy requires Jira ticket approval + deployer human gate

**Production Monitoring:**
- Prometheus + Grafana dashboards active from first PROD deployment
- Langfuse tracing enabled for all LLM calls
- Audit log monitoring for anomalies (Section 12.3 of EU AI Act document)

### 8.4 AI Data Management

**Medallion Architecture:**

Data processed by the Data Engineering Agent flows through the following zones:

| Zone | Purpose | Data State | Controls |
|------|---------|-----------|----------|
| Landing | Raw ingestion, no transformation | Raw strings | Schema capture, source attribution |
| Bronze | Schema enforcement | Typed, validated | Pydantic schema enforcement, reject bad records |
| Silver | Cleaning, deduplication | Cleansed | PII detection scan, data quality checks |
| Gold | Business logic application + analytics-ready aggregations (final layer) | Business-ready | Human approval required for logic changes; lineage documented; change control required |

**Data Catalog:**
- All data assets registered in the data catalog at `frontend/src/app/catalog/`
- Assets include source type, schema, PII classification, medallion zone, and lineage
- PII classification results from `pii_detection.py` are persisted to the `platform_data_classification` PostgreSQL table

**Data Lineage:**
- End-to-end lineage tracked via `dags/dag_utilities/logging/lineage_tracker.py`
- Lineage records capture source, transformation steps, schema versions, and target
- Lineage queryable via the data catalog UI

## 8. Clause 10: Improvement

### 10.1 Continual Improvement

**RAG Feedback Loop:**

`backend/rag/rag_updater.py` implements an active learning feedback loop for the RAG knowledge base:
- Human override events (where the human rejected or modified the AI recommendation) are captured
- Corrected incident resolutions are fed back into the RAG knowledge base as high-quality training examples
- Embeddings are regenerated when runbooks or past incident records are updated
- Retrieval quality scores are tracked over time to measure the improvement effect

**Model Performance Tracking:**
- Langfuse dashboards track confidence score distribution trends over time
- A declining mean confidence score triggers a model quality review
- Prompt versions are tracked and compared; underperforming prompts are retired
- New source types added to APEX are benchmarked against existing types before production release

**Process Improvement:**
- Each quarterly Data Governance Audit generates improvement actions for data quality processes
- Post-incident reviews for any AI-related production incident produce lessons-learned documents
- Guardrail patterns are reviewed quarterly and updated based on new attack vectors

### 10.2 Nonconformity and Corrective Action

**Nonconformity Sources:**
- Internal audit findings
- Guardrail blocks indicating potential systemic input quality issue
- Human rejection rate anomalies (potential model accuracy degradation)
- EU AI Act regulatory updates requiring control changes
- Security incidents or near-misses

**Corrective Action Process:**

| Step | Action | Timeline |
|------|--------|---------|
| 1. Detection | Nonconformity identified via audit, monitoring, or incident | Immediate |
| 2. Containment | Immediate containment action if ongoing harm possible | Within 4 hours |
| 3. Documentation | Logged in Jira as a Compliance issue with "AIMS-NC" label | Within 1 business day |
| 4. Root Cause Analysis | RCA performed by responsible team | Within 5 business days |

## 10. Gap Analysis

The following gaps must be addressed before the platform can be recommended for formal ISO 42001 certification engagement. Gaps are listed in priority order based on certification risk:

### Gap G-001: Formal Competence Records

**Clause:** 7.2 Competence

**Description:** Required competencies for all AI-touching roles are defined (Section 5.3), but there is no systematic process for recording that individuals have met those competency requirements. No training completion records, skill assessments, or qualification evidences are maintained in a retrievable form.

**Certification Risk:** HIGH — Auditors will request evidence that personnel are competent. Absence of records is a non-conformity finding.

**Recommended Action:** Implement a competence tracking system (HR LMS or simple spreadsheet register) recording: role, required competencies, training completed, date, evidence reference, and next review date. Target completion: Q3 2026.

---

### Gap G-002: Formal Awareness Training Program

**Clause:** 7.3 Awareness

**Description:** Personnel are generally aware of the AI Policy and their responsibilities, but no formal tracked awareness training exists. There is no evidence available that all relevant personnel have received and acknowledged AI Policy training, automation bias awareness, or data subject rights training.

**Certification Risk:** HIGH — ISO 42001 requires the organization to demonstrate that persons doing work under the AIMS are aware of the AI policy, their contribution to AIMS effectiveness, and the implications of not conforming.

**Recommended Action:** Develop a mandatory annual AI awareness training module covering: AI Policy, automation bias, human oversight responsibilities, PII handling, and escalation procedures. Track completion with sign-off records. Target completion: Q3 2026.

---

### Gap G-003: Document Management System with Formal Approval Workflow

**Clause:** 7.5 Documented Information

**Description:** AIMS documentation is maintained in the git repository. While git provides version control and change history, it does not provide a formal document approval workflow with documented approver sign-off, review scheduling, or document status management (draft / under review / approved / superseded).

**Certification Risk:** MEDIUM — Auditors require that documented information has controlled approval status. Git commit history demonstrates change tracking but not formal approval by authorized persons.

**Recommended Action:** Implement a lightweight document control process: a document register (spreadsheet or Confluence) tracking document ID, title, version, owner, approver, approval date, and next review date. Formal approvals can be captured as signed PDFs or Confluence page approvals. Target completion: Q4 2026.

---

### Gap G-004: Standalone AI System Impact Assessment Document

**Clause:** 8.2 AI System Impact Assessment

**Description:** The AI System Impact Assessment is currently embedded across `eu_ai_act_compliance.py` (programmatic assessment), `docs/compliance/eu-ai-act.md` (compliance evidence), and this AIMS document. There is no standalone AISA document that has been reviewed and signed off by the AI System Owner and relevant stakeholders as a single governed artifact.

**Certification Risk:** MEDIUM — ISO 42001 requires that impact assessments are maintained as documented information. The substantive content exists but is distributed across multiple documents.

**Recommended Action:** Consolidate the impact assessment into a standalone `docs/compliance/ai-system-impact-assessment.md` document with formal stakeholder review and sign-off recorded. Reference the EU AI Act compliance assessment and AIMS rather than duplicating content. Target completion: Q4 2026.

---

### Gap G-005: Formal Third-Party AI Supplier Risk Assessments

**Clause:** 8.7 Third-Party AI Suppliers

**Description:** The organization has implemented technical controls for third-party AI supplier risk (version pinning, circuit breakers, fallback providers, ToS monitoring) but has not completed formal written risk assessments for each AI model supplier (OpenAI, Anthropic, GCP). Supplier risk assessments should document: supplier capabilities, dependencies, contractual terms, data processing agreements, risk rating, and mitigating controls.

**Certification Risk:** MEDIUM — Auditors will review supplier management evidence. Technical controls alone are insufficient without documented risk assessment rationale.

**Recommended Action:** Produce a formal risk assessment document for each AI model supplier (OpenAI, Anthropic, GCP Vertex AI). Include: service dependency rating, data sharing analysis, SLA review, terms of service prohibited use check, and annual reassessment date. Target completion: Q4 2026.

---

### Gap G-006: Formalized Internal Audit Program

**Clause:** 9.2 Internal Audit

**Description:** An internal audit program has been designed (Section 7.2 of this document) with scope, frequency, and output defined, but the program has not been formally established with: a documented audit plan, designated auditor(s), independence provisions, and records of audit activities. No audit has yet been conducted.

**Certification Risk:** HIGH — ISO 42001 requires evidence that internal audits have been conducted and that findings are addressed. Without at least one completed audit cycle, the organization cannot demonstrate the AIMS is operating as intended.

**Recommended Action:** Formally establish the audit program by: appointing the first internal auditor (can be the AI Safety Officer for initial audit given resource constraints), documenting the annual audit plan, conducting the first AIMS audit within 60 days, and recording findings and any corrective actions. Target completion: Q3 2026 (first audit complete).
