## 1. Executive Summary

The Enterprise Agentic AI Platform operates two AI agent systems: an Incident Management system that automates IT incident resolution via ServiceNow, and the APEX Data Engineering Agent that automates data pipeline generation across 70+ source types. Both systems process sensitive operational and personal data and make consequential automated decisions subject to EU AI Act obligations.

This Information Security Management System (ISMS) document defines the security controls, policies, and procedures governing the platform. It is structured against ISO/IEC 27001:2022 and covers all four Annex A control themes: Organizational, People, Physical, and Technological.

**Certification Intent:** The organization intends to achieve ISO 27001:2022 certification within 18 months. This document represents the current state of implementation and the roadmap to close identified gaps.

**Current Status:**
- Core technical controls implemented (audit logging, PII detection, encryption, CI/CD security scanning)
- Formal ISMS governance structure partially established
- Statement of Applicability (SoA) defined in Section 13
- Gap analysis and remediation roadmap in Section 14

## 3. Information Security Policy (Clause 5.2)

### 3.1 Policy Statement

The Enterprise Agentic AI Platform is committed to protecting the confidentiality, integrity, and availability of all information assets under its control. This commitment extends to:

- Protecting personal data processed by AI agents in accordance with GDPR and EU AI Act requirements
- Ensuring human oversight and approval gates for all consequential AI decisions
- Maintaining immutable audit logs of all AI decisions for a minimum of 7 years
- Applying the principle of least privilege across all system components
- Continuously improving the ISMS through regular risk assessment and control review

### 3.2 Security Objectives

1. Zero unauthorized access to production data in any 12-month period
2. 100% of AI decisions affecting individuals to be audit-logged
3. All PII to be detected and masked before entering the Gold data zone
4. Maximum 2-hour response time for P1 (critical) security incidents
5. Annual security awareness training for all platform contributors
6. Quarterly rotation of all API keys and service credentials

### 3.3 Governance Structure

| Role | Responsibility |
|------|---------------|
| AI Safety Officer | ISMS ownership, EU AI Act compliance, incident command |
| Platform Admin | Technical controls implementation, access provisioning |
| Data Steward | Data classification, lineage, quality governance |
| DevOps Engineer | CI/CD security, infrastructure hardening |
| Development Team | Secure coding, compliance scanning |

## 5. Access Control (Annex A 9)

### 5.1 Access Control Policy

Access to platform resources is governed by the principle of least privilege. Users and service accounts are granted the minimum permissions necessary to perform their assigned functions. Access rights are reviewed quarterly and revoked immediately upon role change or departure.

### 5.2 Role Definitions

| Role | Permissions | Implementation | Access Level |
|------|-------------|----------------|-------------|
| Viewer | Read-only: incident list, pipeline status, workflow state | Frontend read endpoints; no write APIs | L2 and below |
| Approver | Approve/reject pending workflows, view full incident detail | `POST /approve`, `POST /reject` endpoints | L3 read + approval write |
| Engineer | Create pipelines, trigger workflows, view all output | All data-agent API endpoints | L3 full |
| Admin | Full platform access, user management, config changes | Backend API admin routes | L4 |
| Service Account | Machine-to-machine: Kafka consumers, Airflow, CI/CD | API keys with scope restrictions | Role-specific |

### 5.3 Authentication

- Local development: API key authentication via `.env`
- Production recommendation: OIDC with GCP IAM, service accounts per component
- LLM provider APIs: API key stored in GCP Secret Manager, injected at runtime
- GitHub Actions: Repository secrets (never exposed in logs)

### 5.4 Human Approval Gate

All consequential AI decisions must pass through the human approval gate before production execution:

- Incident remediation plans: `POST /incidents/{id}/approve` required before `execute` node runs
- Pipeline deployment to production: approval workflow before Dataproc job submission
- LLM guardrails override: requires Admin role + audit log entry

Implementation: `backend/orchestrator/langgraph_workflow.py` — `await_approval` node; Kafka topic `incident.requires_approval` → `incident.approved`.

### 5.5 Current Gaps and Recommendations

| Gap | Risk | Recommendation | Priority |
|-----|------|----------------|----------|
| No SSO/IAM integration | Credential sprawl | Implement OIDC with GCP IAM | HIGH |
| API key auth for local dev | Weak authentication | Enforce short-lived tokens even locally | MEDIUM |
| No MFA on any endpoints | Account takeover risk | Enforce MFA for Admin and Approver roles | HIGH |
| Role definitions not enforced in code | Privilege escalation | Implement middleware RBAC checks | HIGH |
| Service account key rotation not automated | Stale credentials | Implement Secret Manager rotation triggers | MEDIUM |

## 6. Cryptography (Annex A 10)

### 6.1 Secrets Management

All secrets are managed through a tiered approach:

**Local Development:**
- `.env` file based on `.env.example` — gitignored, never committed
- Reference variables: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `DATABASE_URL`, `LANGFUSE_SECRET_KEY`

**Production:**
- GCP Secret Manager for all credentials
- Secrets injected as environment variables at container startup
- Secret versions maintained for rollback capability
- Access to Secret Manager restricted to specific service accounts

**Key References:**
- `LANGFUSE_NEXTAUTH_SECRET` — Langfuse session signing
- `AIRFLOW__WEBSERVER__SECRET_KEY` — Airflow session security
- `ENCRYPTION_KEY` — Langfuse data encryption
- `POSTGRES_PASSWORD` — Database access
- `NEO4J_AUTH` — Graph database authentication

### 6.2 Encryption at Rest

| Data Store | Encryption Method | Key Management |
|-----------|------------------|----------------|
| GCS buckets | Google-managed AES-256 | Google KMS (default) |
| PostgreSQL | Application-level encryption for sensitive columns | Secret Manager |
| Weaviate | AES-256 at storage layer | Weaviate config |
| Redis | AOF/RDB snapshots — no encryption (local); TLS required for production | N/A local |
| Kafka logs | Plaintext (local); broker-level encryption required for production | Confluent managed |

### 6.3 Encryption in Transit

| Connection | Protocol | Notes |
|-----------|----------|-------|

## 7. Operations Security (Annex A 12)

### 7.1 Audit Logging

`backend/governance/audit_logger.py` provides a comprehensive audit trail:

**23 Event Types Logged:**

| Category | Events |
|----------|--------|
| AI Operations | `AI_DECISION`, `AI_RECOMMENDATION`, `AI_GUARDRAIL_TRIGGERED`, `LLM_CALL`, `CONFIDENCE_THRESHOLD` |
| Human Actions | `HUMAN_APPROVAL`, `HUMAN_REJECTION`, `HUMAN_OVERRIDE`, `USER_LOGIN`, `USER_LOGOUT` |
| Data Operations | `DATA_ACCESS`, `DATA_MODIFICATION`, `DATA_EXPORT`, `PII_DETECTED`, `PII_MASKED` |
| Security Events | `AUTH_FAILURE`, `UNAUTHORIZED_ACCESS`, `SECURITY_INCIDENT`, `PERMISSION_DENIED` |
| System Events | `PIPELINE_CREATED`, `PIPELINE_DEPLOYED`, `SYSTEM_ERROR`, `CONFIG_CHANGED` |

**Storage and Retention:**
- Storage: PostgreSQL `audit_log` table
- Retention: 7 years (EU AI Act Article 12 compliance)
- Immutability: INSERT only — no UPDATE or DELETE operations permitted
- Integrity: Cryptographic hash of each log entry (recommended implementation)

### 7.2 Monitoring

| Tool | Purpose | Coverage |
|------|---------|---------|
| Prometheus | Metrics collection | 50+ platform metrics: latency, error rates, throughput |
| Grafana | Dashboards and alerting | Real-time operational visibility |
| OpenTelemetry (OTEL) | Distributed tracing | Request flow across all services |
| Tempo | Trace storage and query | Correlated with Prometheus metrics |
| Langfuse | LLM call tracking | Prompt/completion logging, cost tracking |
| Frontend `/observability` | User-facing monitoring | Incident and pipeline health |

**Alert Thresholds (recommended):**
- LLM error rate > 5%: Page on-call
- Audit log write failure: CRITICAL alert
- Authentication failure spike (>10/min): Security alert
- Pipeline failure rate > 10%: Engineer notification

### 7.3 Vulnerability Management

**Automated Scanning:**
- `backend/governance/project_validator.py` — scans all Python files for governance compliance:
  - Presence of audit logging in agent nodes
  - Human oversight gates in workflow definitions
  - Confidence thresholds implemented
  - Input/output validation present
  - Explainability requirements met
- `.github/workflows/data-agent-cicd.yml` — CI/CD pipeline includes:
  - Hardcoded secret detection (blocks merge if secrets found)
  - Dependency vulnerability scanning (recommended: add `safety check`)
  - Governance compliance gate

**Manual Reviews:**
- Quarterly dependency audit: review `requirements.txt` for CVEs
- Annual penetration testing (recommended)
- Code security review for all new LLM integration patterns

### 7.4 Change Management

- All changes via GitHub pull requests to protected `main` branch
- CI/CD validation must pass before merge
- Governance compliance scan must pass
- LangGraph workflow changes reviewed by AI Safety Officer
- Auto-merge permitted only for validated DAG generation PRs

### 7.5 Capacity Management

| Component | Strategy | Implementation |
|-----------|----------|----------------|
| Spark/Dataproc | Auto-scaling | GCP Dataproc autoscaling policies |
| Redis | LRU eviction | `maxmemory-policy allkeys-lru` |

## 11. Information Security Incident Management (Annex A 16)

### 11.1 Incident Classification

| Priority | Category | Examples | Response SLA |
|----------|----------|---------|-------------|
| P1 | PII/data breach | Unauthorized PII exposure, audit log compromise | 2 hours |
| P2 | Unauthorized access | Failed login spike, privilege escalation | 4 hours |
| P3 | Availability | Service outage, Kafka lag, DB unavailability | 8 hours |
| P4 | Integrity | Data quality failure, audit gap | 24 hours |

### 11.2 Incident Response Procedure

The platform's own Incident Management system handles security incidents via the 12-node LangGraph workflow:

1. **Detection** — Prometheus alerts, Grafana dashboards, or manual report
2. **Logging** — `SECURITY_INCIDENT` event logged to audit trail immediately
3. **Classification** — P1/P2/P3/P4 assigned by AI Safety Officer
4. **Containment** — Isolate affected component; revoke compromised credentials
5. **Evidence Preservation** — Audit logs are immutable (INSERT only in PostgreSQL)
6. **Notification** — P1: notify DPO/supervisory authority within 72 hours (GDPR Art. 33)
7. **Eradication** — Root cause addressed, credentials rotated
8. **Recovery** — Service restored with enhanced monitoring
9. **Post-Incident Review** — Within 5 business days; findings documented

### 11.3 Evidence Preservation

Audit logs in PostgreSQL are immutable by design:
- INSERT only — no UPDATE or DELETE SQL permitted on the `audit_log` table
- PostgreSQL row-level triggers enforce immutability (recommended)
- Log export to immutable GCS bucket with object versioning enabled
- Forensic queries via audit log API: `GET /governance/audit-logs?incident_id={id}`
